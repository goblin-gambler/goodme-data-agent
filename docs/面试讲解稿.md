# 古茗智数 · AI 面试项目讲解稿

> 适用场景：AI 应用开发、LLM 工程、数据智能/Text2SQL 方向面试。
> 使用方式：先背熟 2 分钟版；面试官追问时按第 4 章展开；不要逐字背长版。

## 0. 讲之前记住三条原则

1. **先讲问题，再讲方案**：不要一上来报技术栈，先说"业务人员不会写 SQL"这个痛点。
2. **每个技术选择都要能回答"不用它会怎样"**：为什么不全量塞 Schema、为什么用 ES 又用 Qdrant、为什么要 12 个节点。
3. **不夸大**：项目来源、能力边界、没做过的事，如实说。面试官更看重你能否解释清楚，而不是你是否从零手写。

## 1. 三个时长版本

### 1.1 十秒版（自我介绍里带一句）

> 我做了一个面向茶饮连锁经营分析的自然语言问数系统：用户用中文提问，系统通过 Schema RAG 召回相关的表、字段、指标和取值，用 LangGraph 编排 12 个节点生成并校验 SQL，最后通过 SSE 把执行过程和结果流式返回前端。

### 1.2 三十秒版

> 这个项目的出发点是：让业务人员不写 SQL 也能查数。
>
> 难点不在"让模型写一条 SQL"，而在三件事：选对表、用对指标口径、写对过滤值。所以我没有把全部表结构塞给模型，而是先做了一层元数据知识库：字段和指标走 Qdrant 向量召回，枚举值走 Elasticsearch + IK 全文检索。
>
> 召回结果经过表和指标两轮过滤后，再交给模型生成 SQL；生成后用 `EXPLAIN` 校验，失败就带着数据库错误回到修正节点。整个链路用 LangGraph 串成 12 个节点，每个节点的进度通过 SSE 推给前端。
>
> 数仓是 9 张表的星型模型，覆盖 2025 年第一季度约 4.8 万笔订单。

### 1.3 两分钟版（逐字稿）

> 我讲一个自然语言问数的项目，叫古茗智数。
>
> **背景**：门店饮品零售的分析需求集中在订单、营收、会员、商品、渠道几个维度，但业务人员直接写 SQL 有三个问题：不熟悉 9 张表的 Join 路径；不理解 GMV、销售额、客单价这些指标的口径；大模型直接生成 SQL 又容易编字段、选错表、漏掉订单状态过滤。
>
> **核心思路**：不是让大模型直接写 SQL，而是先检索、再生成、最后校验。系统有一条离线链路和一条在线链路。
>
> 离线链路把元数据整理成知识库：表、字段、指标和字段指标关系统一存在 MySQL；字段和指标分别向量化到 Qdrant；低基数的枚举值，比如大区、茗星等级、渠道，写进 Elasticsearch，用 IK 分词做全文检索。
>
> 在线链路是一个 12 节点的 LangGraph 工作流。用户问题进来后，先用 Jieba 抽关键词，再并行做三路召回：字段召回解决"用哪些列"，指标召回解决"按什么口径算"，取值召回解决"过滤条件里的值怎么写"。三路结果合并时，会补齐指标依赖的字段、字段的真实取值和主外键。
>
> 合并之后不是直接生成 SQL，而是先做两轮过滤：让模型只回答"保留哪些表、哪些字段、哪些指标"，真正的结构裁剪由程序完成。这样模型不用重写复杂结构，输出更稳定。
>
> 然后补上当前日期和数据库方言，生成一条 SQL。生成后先 `EXPLAIN`，让数据库真正解析一次；失败就把错误信息、原问题和完整上下文一起交给修正节点，修正后再执行。前端通过 SSE 实时看到每个节点的状态，最后拿到结果表格。
>
> **数仓**是 9 张表的星型模型：7 张维度表、2 张事实表，71 个字段、16 个指标。这里有个关键设计：订单表和订单明细表是双粒度，Join 之后不能对订单级金额求和，否则一个订单有多条明细会重复计数。所以 GMV 用订单表的实收金额，明细维度的销售额用明细表的金额，Prompt 里也单独加了这条约束。
>
> **结果**：2025 年第一季度 48,409 笔订单、70,802 条明细，全量 GMV 约 130.8 万。问"按茗星等级统计订单量和客单价"，四个等级都能正确返回；问渠道占比，订单量占比和 GMV 占比也都能算对。
>
> **边界**：目前只支持单轮、只读、单条 SQL，没有多轮上下文、图表和权限控制；只读约束目前主要靠 Prompt，数据库层还没有强制的只读账号和语句白名单，这是下一步要补的。

## 2. 背景：为什么不是"直接让大模型写 SQL"

业务人员直接写 SQL 的三个现实问题：

| 问题 | 具体表现 | 对应设计 |
| --- | --- | --- |
| 不知道表结构 | 9 张表、71 个字段，Join 路径不熟 | 字段召回 + 主外键补齐 |
| 不知道指标口径 | GMV 和销售额是不是一个东西？客单价怎么算？ | 指标召回 + 指标定义写进 Prompt |
| 不知道真实取值 | 库里存的是"华东"还是"华东大区"？ | 字段取值召回（ES） |

大模型直接生成 SQL 的额外风险：

- 编造不存在的字段；
- 选错事实表，或订单级/明细级金额混用；
- 漏掉 `order_status = '已完成'`；
- 生成多条 SQL 或写操作。

所以系统的定位不是"Text2SQL 模型"，而是**受约束的 Schema RAG + SQL 闭环**：先把与问题相关的元数据召回出来，再让模型在候选范围内推理。

## 4. 五个核心设计（面试主战场）

每个设计都按「不用它会怎样 → 怎么做 → 效果 → 可能被追问」来讲。

### 4.1 Schema RAG：为什么不全量塞 Schema

**不用它会怎样**：9 张表 71 个字段全塞进 Prompt，token 变多只是表面问题，更严重的是噪声——模型要在几十个字段里选，容易选错表、混用相似字段（比如 `order_amount` 和 `actual_amount`）。

**怎么做**：

- 字段和指标分别建 Qdrant collection，各自召回，互不干扰；
- 一个字段拆成多个向量点：字段名、描述、每个别名各一个，扩大"成交额/实收/收入"这类不同说法的命中入口；
- 召回阈值 0.6、每个关键词 top 20，按字段 ID 去重。

**效果**：Prompt 里只保留与问题相关的表和字段，生成阶段的选择空间被压缩。

**追问准备**：

- "阈值 0.6 怎么来的？" —— 经验值 + 观察召回结果，没有做系统调参；如果要严谨，需要标注一批问题和正确字段，扫阈值看召回率/精度。
- "为什么不直接用微调模型？" —— 数据量不够；schema 和指标会变；RAG 改配置就能更新，微调要重训。

### 4.2 三路召回：分别解决什么

| 召回 | 数据源 | 解决的问题 | 例子 |
| --- | --- | --- | --- |
| 字段 | Qdrant | 用哪些列、哪些表 | "销售额" → `item_amount`、`actual_amount` |
| 指标 | Qdrant | 按什么口径算 | "客单价" → GMV / 订单量 |
| 取值 | Elasticsearch | 过滤值怎么写 | "顶流茗星" → `member_level` 的真实枚举 |

**关键点**：三路召回之前都有一次 LLM 关键词扩展，因为用户说法和元数据表述经常不一致（"卖了多少杯" vs "出杯量"）。

**代价**：一次问答至少多 3 次 LLM 调用。这是用延迟换召回率，目前没有做缓存和合并，是明确的优化点。

**为什么取值用 ES 不用向量**：枚举值是精确匹配问题，"华东"和"华东大区"在向量空间可能很近，但业务上必须写对；ES + IK 的 `match` 查询更直接。低基数字段才同步进 ES，高基数字段不进，避免索引膨胀。

### 4.3 过滤节点：模型只做选择，程序做裁剪

**不用它会怎样**：把召回的所有表和指标直接交给生成模型，上下文长且互相干扰；让模型输出裁剪后的完整结构，又容易出现字段丢失、结构变形、JSON 解析失败。

**怎么做**：

- `filter_table`：模型只返回 `{表名: [字段名]}`，程序按这个结果从原始结构里裁剪；
- `filter_metric`：模型只返回需要的指标名列表，程序保留完整定义。

**效果**：模型输出结构简单、可解析；裁剪结果可预测、可单测。

**追问**："模型选错了怎么办？" —— 当前没有兜底重试；可以增加"必选字段校验"（比如事实表的主键、时间字段、指标依赖字段强制保留），或者让过滤失败时回退到不过滤。

### 4.4 LangGraph：12 节点与状态设计

**拓扑**：

```text
START → extract_keywords
          ├─→ recall_column ─┐
          ├─→ recall_value  ─┼─→ merge_retrieved_info
          └─→ recall_metric ─┘         ├─→ filter_table ─┐
                                       └─→ filter_metric ─┴─→ add_extra_context
                                                                  → generate_sql
                                                                  → validate_sql
                                                                     ├─ 无误 → run_sql → END
                                                                     └─ 有误 → correct_sql → run_sql
```

**为什么是 12 个节点**：不是为了数量，而是每个节点职责单一、可观测、可单独调试。三路召回并行，是为了把三次检索的延迟叠起来，而不是串行相加。

**State 与 Context 分离**：

- `DataAgentState`：只放可序列化的业务数据（问题、关键词、召回结果、SQL、错误）；
- `DataAgentContext`：放本次执行复用的外部依赖（MySQL/Qdrant/ES 仓储、Embedding 客户端）。

好处是图状态可打印、可回放、可测试；连接池和客户端不会混进状态里。

**追问**："节点能不能合并？" —— 可以，比如两个过滤节点能合成一个；但拆开后前端能逐步展示，排错时也能定位到具体阶段，是刻意保留的粒度。

### 4.5 SQL 闭环：生成不是终点

**流程**：

1. `generate_sql`：Prompt 约束 10 条规则，只输出一条纯 SQL；
2. `validate_sql`：执行 `EXPLAIN <sql>`，让数据库真正解析；
3. 解析失败：错误写进 state，条件边进入 `correct_sql`；
4. `correct_sql`：带上原问题、原 SQL、数据库错误和完整上下文做最小修正；
5. `run_sql`：执行并返回结果。

**Prompt 里最重要的三条约束**：

- 只能用提供的表和字段，禁止编造；
- 指标有定义时必须遵守口径和订单状态过滤；
- 订单表和明细表 Join 后，按明细维度统计金额必须用 `item_amount`，禁止对订单级金额求和。

**边界要主动说**：

- `EXPLAIN` 只能证明 SQL 能被解析，不能证明语义正确、性能可接受；
- 目前校正只做一次，且校正后直接执行，没有再次 `EXPLAIN`；
- 只读约束主要靠 Prompt，数据库层没有强制只读账号和语句白名单。

这三条主动讲出来，比被追问出来更好。

### 4.6 可观测性：SSE + request_id

- 每个节点通过 `runtime.stream_writer` 写 `progress` 事件；
- `run_sql` 写 `result`，异常包装成 `error`；
- 前端用 `fetch` + `ReadableStream` 解析 SSE，因为 `EventSource` 不支持 POST；
- 后端用 `ContextVar` 注入 `request_id`，loguru 每条日志都带，方便串起一次请求。

## 5. 数仓设计：体现业务理解

### 5.1 星型模型

9 张表、71 个字段：

- 7 张维度表：区域、门店、商品、会员、渠道、促销、日期；
- 2 张事实表：`fact_order`（订单粒度）、`fact_order_item`（明细粒度）。

### 5.2 双粒度事实表与扇出（必须能讲清楚）

`fact_order` 一行一个订单，`fact_order_item` 一行一个饮品 SKU。

- 订单粒度：GMV、订单量、客单价、折扣率、会员订单占比；
- 明细粒度：销售额、出杯量、杯单价、新品销量占比、糖度/冰量分布。

**扇出问题**：一个订单有多条明细，两表 Join 后订单级金额会重复出现。如果对 `actual_amount` 求和，GMV 会被放大。

**解决**：

1. 指标拆成两个口径：GMV 用 `fact_order.actual_amount`，销售额用 `fact_order_item.item_amount`；
2. Prompt 第 7 条明确禁止 Join 后对订单级金额求和；
3. 指标描述里写清楚适用维度，召回时一起给模型。

**追问**："怎么验证没有扇出？" —— 全量 GMV 1,308,418.15，和各渠道 GMV 之和一致；如果扇出，数字会明显偏大。

### 5.3 业务口径

- 会员等级：潜力茗星 / 人气茗星 / 当红茗星 / 顶流茗星；
- 门店类型：直营店 / 加盟店；
- 渠道：到店自提 / 小程序外卖 / 美团外卖 / 饿了么外卖；
- 糖度：十分甜 / 七分甜 / 五分甜 / 三分甜 / 微糖；
- 冰量：正常冰 / 少冰 / 去冰 / 温 / 热；
- 商品系列：超 A 芝士家族等。

这些不是装饰，而是取值召回和指标口径的基础。

## 7. 三个难点故事（STAR）

挑一个讲，不要全讲。

### 7.1 扇出导致 GMV 翻倍

- **S**：订单表和明细表 Join 后统计销售额，结果明显偏大。
- **T**：找到原因并保证所有指标口径正确。
- **A**：定位到一对多 Join 的扇出；把指标拆成订单级和明细级两个口径；Prompt 增加强制约束；指标描述写清适用维度。
- **R**：全量 GMV 与各渠道之和一致，明细维度销售额不再重复计数。

### 7.2 中文枚举值召回不稳定

- **S**：用向量检索"华东""顶流茗星"时，经常召回相似但不正确的值。
- **T**：让过滤条件的值写对。
- **A**：把低基数枚举值写进 ES，使用 IK 分词和 `match` 查询；召回结果合并回字段的 `examples`，生成 SQL 时作为参考。
- **R**：地区、会员等级、渠道等过滤条件能稳定命中真实取值。

### 7.3 知识库重复构建

- **S**：重复执行构建脚本后，向量点和元数据出现重复。
- **T**：让构建结果可复现。
- **A**：确认构建是追加写、不幂等；重建前清空 Meta MySQL 四张表、两个 Qdrant collection 和 ES 索引；数据脚本固定随机种子并先 TRUNCATE。
- **R**：每次重建后的数量稳定在 9/71/16/45、361/89、234。

## 9. 高频追问与回答要点

### 9.1 检索相关

**Q：为什么用 Qdrant 和 Elasticsearch 两套检索？**
A：对象不同。字段和指标是语义匹配，适合向量；枚举值是精确字面匹配，适合全文检索。用一套会有一边效果不好。

**Q：召回阈值和 topK 怎么定？**
A：当前是 0.6 和 20，属于经验值。严谨做法是标一批"问题 → 正确字段/指标"，扫阈值看召回率和上下文长度，再定参数。目前没做系统调参，这是可改进点。

**Q：召回不准怎么办？**
A：三个方向：一是关键词扩展，弥补用户说法和元数据表述的差异；二是合并时补主外键和指标依赖字段，避免召回漏掉 Join 必需列；三是过滤阶段兜底必选字段。再往上可以做 rerank。

**Q：为什么召回前还要调 LLM 扩展关键词？**
A：解决词汇鸿沟，比如"卖了多少杯"要能召回"出杯量"。代价是 3 次额外调用，可以合并成一次调用或加缓存。

### 9.2 编排相关

**Q：为什么用 LangGraph，不用普通的函数调用？**
A：需要并行召回、条件分支、状态传递和过程可观测。普通函数也能写，但分支和状态会散在代码里，LangGraph 把拓扑显式化，前端也能按节点展示进度。

**Q：State 和 Context 为什么分开？**
A：State 只放可序列化的业务数据，便于打印、回放、测试；Context 放连接池和客户端，不进入图状态。

**Q：12 个节点是不是过度设计？**
A：可以合并，但拆开的价值是职责单一、可观测、可单独调试。三路召回并行是实打实的延迟收益。

### 9.3 SQL 与安全

**Q：怎么保证模型不写 UPDATE/DELETE？**
A：目前是 Prompt 约束"只生成查询" + 单条 SQL，数据库层没有强制。正确做法是给只读账号、加语句白名单、设置超时和返回行数上限。这是当前明确的缺口。

**Q：EXPLAIN 能保证 SQL 正确吗？**
A：不能。它只能证明语法、表名、字段名能被数据库解析，不能保证业务语义正确、结果正确、性能可接受。

**Q：校正失败怎么办？**
A：当前只校正一次，校正后直接执行；如果仍失败，`run_sql` 抛错，前端收到 error 事件。改进方向是"校验 → 校正"循环加最大次数，并在每次校正后重新 EXPLAIN。

**Q：怎么防止 SQL 注入？**
A：SQL 由模型生成、不接收用户拼接的原始 SQL；但仍应加只读账号和语句白名单，不能只依赖 Prompt。

### 9.4 评测与效果

**Q：准确率多少？**
A：没有标注集，所以不报准确率。当前用固定问题集做回归验证，比如茗星等级、渠道占比、区域 TopN。要严谨评测，需要构建"问题 → 期望结果"的数据集，看执行成功率和结果一致率。

**Q：怎么判断一条 SQL 是对的？**
A：两层：执行层看是否通过 EXPLAIN、是否返回结果；业务层看结果能否用手工 SQL 或已知基线对上。比如全量 GMV 1,308,418.15 就是基线。

**Q：延迟和成本怎么样？**
A：瓶颈在 LLM 串行调用，一次问答至少 6 次（3 次扩展 + 2 次过滤 + 1 次生成）；检索本身是毫秒级。优化方向是合并关键词扩展、缓存常用问题、把过滤和生成做并行或小模型化。

### 9.5 扩展性

**Q：怎么支持多轮？**
A：需要会话级状态、指代消解（"那上个月呢"）、上一轮 SQL 复用。当前 State 是一次性的，扩展时要引入 session 存储。

**Q：怎么支持权限和租户？**
A：在生成前注入行级过滤条件，或在执行前重写 SQL；同时加 SQL 审计。不能只在 Prompt 里写"只查本店"。

**Q：新增一个指标要改什么？**
A：改 `conf/meta_config.yaml`，然后清空 Meta MySQL、Qdrant、ES 里的旧数据并重建知识库。当前构建是追加写、不幂等，这是已知问题。

**Q：数据更新了知识库怎么办？**
A：目前是全量重建，约 40–51 秒。数据量大后要做增量同步和版本管理。

**Q：为什么不做图表？**
A：当前定位是"先保证查得对"，图表是展示层扩展；结果表格已经能验证口径。

## 10. Demo 脚本（现场演示用）

**准备**：Docker 服务、后端 8000、前端 5173 都已启动。

1. 打开首页，用一句话说明："左边是示例问题，中间是问数区。"
2. 点击示例"按茗星等级统计 2025 年第一季度的订单量和客单价"。
3. 指着执行流程说："这里是 12 个节点，三路召回是并行的，SQL 校验失败会走右边的校正分支。"
4. 结果出来后说："四个等级、订单量、客单价都正确，客单价都在 28 元左右。"
5. 再问一个渠道占比，强调"占比和两位小数"也能处理。
6. 最后主动说边界："目前是单轮、只读、单条 SQL，没有做多轮和权限。"

**备用问题**：

- 统计 2025 年 3 月各饮品品类的出杯量和销售额
- 查询华东地区 2025 年第一季度销售额最高的前 5 家门店
- 2025 年第一季度上市的新品中，哪些卖得最好？
